# Odin C++ Binding Proof of Concept

Proof of Concept for binding C++ in Odin directly without a C wrapper

C++ and original harness generated by Claude Opus 5.5, v2 adjusted to be more Odin idiomatic by me

## Notes
 - this will likely only work for amd64, x86 uses __thiscall which isnt an option with Odin/LLVM
 - `dumpbin /exports <name>.dll` to list mangled exports
 - `dumpbin /symbols <name>.obj` to list all symbols noisily but with demangled signature
   - msvc also provides `undname` to demangle
   - could also try to bind a mangled name with nonsense and the msvc linker error will demangle it
 - `cl <flags> /Zs <main>.cpp /d1reportAllClassLayout` to verify structure and vtable layouts
   - or `/d1reportSingleClassLayout<ClassName>` for more targeted verification
 - virtual methods export the concrete method and the constructor fills the vtable correctly, convention to prefix with `_virtual_` or not bind at all
 - various constructors return `this` even if it is often discarded, convention to name them `_ctor` (`_dtor`) `_cctor` `_caop` `_mctor` `_maop`
   - this seems to be different with itanium
 - virtual destructor takes a second u32 argument, see `Scalar_Deleting_Destructor_Flags`, that can optionally free or change whether to scalar or vector
   - this is different with itanium, there the vtable contains two entries, first the complete then the deleting destructor
 - methods that return a struct take a hidden `T* sret` argument between `this` and the regular arguments and return `sret` by pointer anyway
   - this is different on itanium, there the first argument is `T* sret` then `this` then regular arguments, and is only used for types >16 bytes (?)
 - a classes new virtual methods are added onto the first inheritances vtable while all following are left as is, see `Animal`
 - static member variables might be tricky to bind and error at linktime, try `-use-single-module` and additionally binding the `__imp_` prefixed pointer version, also convention to prefix them with `_private_` or `_protected_` if not public, see `Animal_s_alive`
 - odin allows default arguments on vtable procs, use them
 - non virtual functions with default arguments will need a wrapper, convention to prefix the binding with `_`, see `Penguin_slide`
 - overloaded non virtual methods will need a proc group, convention to suffix the bindings with the arguments types (other than `this` and `ret`)
 - const reference arguments `const T&` can be bound with `v: ^T` or `#by_ptr v: T`, both work
 - `new` and `delete` are usually exported and can be bound for heap allocations, might not show up in dll exports
   - `??2@YAPEAX_K@Z (void * __cdecl operator new(unsigned __int64))`
   - `??3@YAXPEAX_K@Z (void __cdecl operator delete(void *,unsigned __int64))`
   - `??_V@YAXPEAX_K@Z (void __cdecl operator delete[](void *,unsigned __int64))`
 - inline methods *might* not be exported, either translate them to odin directly or leave them out of the binding with a warning
